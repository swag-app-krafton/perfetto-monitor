Decision note · 23 September 2026

Flashlight + Perfetto: observations and the path to take

Flashlight is useful for repeatable Android performance audits across native and React Native code. Perfetto should remain this repository's only canonical event timeline. The controlled experiment has now run: the two cannot share a device at the same time, in either order, so they run as separate lanes.

Phase 0 result · 23 September 2026

Running both at once destroys the Perfetto trace

Tested on a Vivo V2514 with Swag Pay, using Flashlight's own sampler (@perf-profiler/profiler 0.10.11, the code flashlight test runs) and swagperf's manual Perfetto session. Four modes, three repetitions each, in rotating order. Every run tapped the bottom tabs 10 times in each of three 10-second windows, logging each tap on the device's boot clock, so each window should hold exactly 10 screen markers. Flashlight joins a recording

From the moment it starts, Perfetto records no scheduler events, no app slices, no screen markers and no RAM samples. It does not recover after Flashlight stops. The app kept rendering normally: the frame timeline, which reaches Perfetto from SurfaceFlinger rather than the kernel, held at 102–105% of the control.

Perfetto starts second

The session starts without error but records no scheduler events, no counters and no process names, so nothing can be attributed to the app. Perfetto logs no error that the control does not also log: the failure is silent.

Flashlight is unaffected

Its sampler parsed 17.5–18.3 frames per 500 ms measure in every mode, 98–103% of running alone. The damage runs one way.

Why. Snapshots of the device's tracing state at each step show what Flashlight's start does to a running Perfetto session: it switches the sched_switch event off, shrinks the kernel trace buffer from 32 MB to 2 MB, replaces the atrace categories with view alone, and clears the app list that lets Swag Pay's markers through. Stopping it sets tracing_on to 0 while Perfetto is still recording. Its source explains the first part: it runs atrace --async_stop, starts atrace -c view, and reads trace_pipe from the same kernel buffer. It also leaves its atrace settings behind after it exits.

Decision (confirmed 23 September 2026): the two profilers stay separate. Same-run sampling with Flashlight is ruled out, and not something tuning will fix. Flashlight runs only as a separate audit lane, on a device nothing else is recording. Anything that must line up with Perfetto's timeline is derived from the Perfetto trace itself. Two requirements follow: a Perfetto capture must refuse to start while Flashlight's profiler is running on the device, because the failure is otherwise silent; and a Flashlight audit must reset atrace when it finishes. The experiment is reproducible with experiments/flashlight-concurrency/.

Executive decision

Use both tools, but give them different ownership

Adopt

Use Flashlight for repeated audits, portable reports, JS-thread visibility, and external/production-app comparisons.

Tested: ruled out

Its programmatic polling was run beside Perfetto on a real device. It stops Perfetto's scheduler, marker and RAM data outright, in either order. See the Phase 0 result above.

Do not assume

Do not treat two independent captures as one event-level timeline or allow two measurement controllers to own the device concurrently.

What was observed

Fit, benefits, and caveats

Hybrid-app fit

  • Flashlight explicitly targets Android native, React Native, and Flutter apps.
  • Its process/thread measurements cover a native + RN hybrid because both execute inside Android processes.
  • RN insight depends on recognizable JS thread names; it does not know product screens or CTAs without app markers.

Useful output

  • Repeated test runs and averaged results.
  • CPU, memory, frame/performance score, and per-thread views.
  • JSON output plus a shareable report.
  • Official Maestro integration.

Measurement caveats

  • Scores vary materially with user behavior; automation and multiple iterations are required.
  • Maestro process startup can pollute command-runtime/TTI measurements.
  • Polling consumes device resources and ADB bandwidth; overhead must be measured on target devices.
  • Flashlight and Perfetto metric definitions must not be compared as if identical.

Concurrency status: tested and ruled out. Full Flashlight measure/test and the narrower pollPerformanceMeasures API start the same sampler, and it breaks a Perfetto recording on the same device. Run one measurement tool per device.

Recommended implementation path

Roll out in five controlled steps

Define metric ownership. Perfetto owns time-aligned screen/action/API, CPU, RAM and frame evidence. Flashlight initially owns only its audit score/report and RN thread summary.
Run a compatibility matrix. Done, 23 September 2026: Perfetto only, Flashlight only, and the sampler joining or preceding Perfetto, three repetitions each. The sampler breaks the trace every time, so the remaining steps assume separate runs.
Add a separate Flashlight CI lane. Reuse the exact approved Maestro flow, device class, build, test data and thermal preparation. Store results.json as an immutable artifact.
Import summaries, not a false timeline. Add Flashlight aggregates to the dashboard beside the Perfetto run group. Display whether evidence is same_run, same_cohort, or unrelated.
Derive same-run metrics from Perfetto. Same-run sampling failed the trace-integrity gate outright, so per-thread CPU (including the React Native JS thread) comes from the Perfetto trace's own scheduler data instead.
Proposed go/no-go gates

Compatibility must be demonstrated, not inferred

Trace integrity: failed

  • No missing Perfetto data sources.
  • No lost screen/action markers.
  • No trace start/stop interference.

Observer overhead

  • Proposed gate: ≤3% median and ≤5% p95 funnel-duration change.
  • No material jank, CPU, RAM, or thermal shift caused by sampling.

Operational safety

  • One leased device and one executor.
  • No competing ADB commands during critical transitions.
  • Clean shutdown and artifact recovery after failure.
Combined-view contract

Store provenance so the dashboard cannot overstate correlation
