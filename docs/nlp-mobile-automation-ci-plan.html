Architecture recommendation · 23 September 2026

NLP mobile automation that stays deterministic in CI

A plan for turning plain-language funnels into safe, versioned Android test plans, executing them with Maestro, and correlating every screen and action with a single Perfetto trace.

Feasible Android first Native + React Native hybrid LLM outside measured execution

Executive verdict

Build this as a contract-grounded compiler, not an unconstrained UI agent. Natural language should resolve to a typed intent and a frozen action plan. Policy validation happens before execution. Maestro then runs the approved plan while Perfetto records one canonical timeline.

Use ARTEMIS to explore unknown screens, reproduce failures, and propose new paths. Do not make it the default performance-sensitive CI executor.

Core invariant Probabilistic planning.

3 · Correlated performance evidence

One execution, one Perfetto timeline, stable IDs everywhere

Inside the measured run

  • Start Perfetto and wait until tracing is active.
  • Execute the already-frozen Maestro plan.
  • Emit screen:<id> and action:<id> spans from the app.
  • Attach run_id, step_id and backend correlation ID.
  • End capture, extract deterministic metrics, then evaluate gates.

Outside the measured run

  • LLM interpretation and plan generation.
  • ARTEMIS exploration or visual reasoning.
  • Self-heal suggestions and selector repair.
  • Human approval and contract promotion.
  • Non-deterministic narrative analysis.

For backend-powered screens, use stable operation IDs plus page/action keys—not raw URLs containing user data. Link Perfetto spans to server telemetry using a correlation ID; do not attempt to copy full backend payloads into the device trace.

4 · Where ARTEMIS fits

Good exploration technology; not the default regression runner

Use it for

  • Discovering unknown UI paths and custom RN/Compose surfaces.
  • Producing candidate screen/widget/action records.
  • Reproducing failures with screenshots, hierarchy and logs.
  • Nightly exploratory and resilience testing.

Do not use it for

  • Precise timing or performance thresholds.
  • Every-PR deterministic pass/fail execution.
  • Automatic financial action repair or selector promotion.
  • Unreviewed writes into the canonical contract catalog.

Why

ARTEMIS reports roughly 3–5 seconds per Flash step and 15–40 seconds per Pro step. Flash lacks a pre-execution safety net and checkpoint verification; Pro adds those controls at substantially higher latency. Its 99%+ AndroidWorld result is encouraging, but it is not yet evidence for this app, device fleet, or financial safety model.

6 · Delivery plan

Build capability in six controlled increments

Phase 0 · Baseline and invariants

Freeze the current POC behavior, add tests around policy/compiler/matcher, and separate read-only analysis from write/promotion operations.

Exit: reproducible POC with CI, pinned dependencies and no catalog mutation during planning.

Phase 1 · Canonical contract model

Define IDs and lifecycle for screens, widgets, actions, transitions, backend operations, assertions and trace markers. Version it with the app build.

Exit: two existing funnels represented without hard-coded action arrays.

Phase 2 · Constrained NLP planner

Introduce Intent IR and Plan IR, retrieval over the contract graph, structured output, reachability checks, policy decisions and plan hashes.

Exit: approved paraphrases compile to the same canonical plan; unknown requests refuse safely.

Phase 3 · Deterministic execution

Compile plan IR to Maestro adapters, manage test data and device leases, and publish JUnit plus a signed run manifest.

Exit: repeatable device smoke with measured flake rate.

Phase 4 · Perfetto correlation

Wrap the frozen execution in one trace and emit stable screen/action/API markers. Join backend spans by correlation ID.

Exit: a screen/action waterfall with CPU, RAM, frame and backend timings from the same run.

Phase 5 · ARTEMIS discovery lane

Evaluate ARTEMIS on a private benchmark, let it propose contract diffs and repair candidates, and require review before promotion.

Exit: proven discovery uplift without weakening deterministic gates.
7 · Decisions needed before schemas

Follow-up questions

Which backend source owns the screen truth?

Is there already a versioned page/widget manifest behind /page/fetch, or must the automation platform derive one from responses and UI inspection?

Where will CI run real devices?

Self-hosted Android device rack, managed device farm, or emulators—and how many parallel jobs are expected?

What is allowed to execute automatically?

Should financial-like flows always require mock backend + test PIN + explicit approval, or can approved staging fixtures run unattended?

Which funnel becomes the reference slice?

Choose one native → RN → backend-heavy path so contracts, traces, and CI gates are designed against the hardest real seam.

Can the app emit stable semantic IDs?

We need durable screen_id, widget_id and action_id values across native and RN layers; text and coordinates are fallback evidence only.

What data may leave the network?

ARTEMIS/LLM evaluation needs a clear rule for screenshots, accessibility trees, backend payloads, PII redaction and model-provider residency.
