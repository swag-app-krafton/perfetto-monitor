Screenshot testing with Maestro

A visual regression lane for swagperf. Maestro flows take a screenshot at named checkpoints, swagperf compares each one against an approved baseline for that app, cohort and device class, and an unexpected change fails the run until someone approves it. Designed and deliberately parked: nothing is built yet.

F-012 Parked · backlog · P3 Android first Separate lane from Perfetto runs Revisited by the product-manager skill
How a run works

The lane, end to end

  1. Flowflows/<pkg>/<flow>.yaml with takeScreenshot checkpoints
  2. Maestromaestro --device <serial> test into a run folder
  3. CollectScreenshots from manifest.json, failures from commands.json
  4. NormaliseMask the status bar and anything live, such as Home's camera preview
  5. DiffPixel compare against the baseline for this cohort and device class
  6. GateExit 0 pass, 1 fail, 2 waiting for approval
  7. ApproveA person reviews the diff in the dashboard; it becomes the new baseline

Every stage is deterministic arithmetic. No screenshot is ever sent to the model, the same rule swagperf already keeps for traces.

Platforms

Android first

The iOS simulator follows. The comparison doesn't depend on the platform.

Why swagperf compares, not Maestro. Maestro 2.10 ships assertScreenshot (path, thresholdPercentage, cropOn, optional), checked in the installed jar. It stops the flow at the first mismatch, has no region masks, and has no per-device baselines or approval step. So flows only take screenshots with takeScreenshot, and swagperf does the comparison.

Your question

Several cohorts, each with its own layout: how robust is this?

Pixel diffing on its own isn't robust across cohorts. It only knows "different from the baseline", so cohort B compared with cohort A's baseline reads as a regression. Four additions make it robust.

  1. Cohort goes into the baseline key. Baselines are keyed (app, cohort, device class, flow, checkpoint), so each cohort has its own.
  2. Pin the cohort instead of inferring it. Each cohort is driven by a fixed test account (the POC already has config/test-data/) or a forced-cohort override in debug builds.
  3. Check the cohort at run time. The app reports its cohort, for example as a cohort:<id> trace marker next to its existing screen: and step: markers, or as a test tag the flow asserts. A mismatch makes the run an error, never a changed diff. It's the same idea as the guard that stops an empty trace from passing.
  4. Freeze the data and record the layout. Run against the mock environment, with recorded /page/fetch responses per cohort; against live staging, offers, balances and banners change daily. Record a hash of each checkpoint's layout response, or its layout-contract version from ADR 0001. A diff can then say layout_changed (the backend sent a new layout: expected, needs approval) or render_changed (same layout, different pixels: likely an app regression).

The limit: baselines multiply as cohorts × device classes × checkpoints, so 5 × 3 × 20 is 300 images to approve. Keep pixel baselines for a handful of key screens per cohort, and cover the rest with the size-independent layout checks below.

Your question

How do the baseline screenshots stay up to date?

An intentional change is approved, not re-recorded

A UI change arrives as changed with a diff overlay. A reviewer approves it in the dashboard, one checkpoint at a time or in bulk per flow, cohort or device class, with a note. Every approval is kept (who, when, which build, why), so one can be rolled back.

The whole matrix in one pass

A rebaseline run covers every cohort and device class. Identical changes (the same region moved on all three device classes) are grouped so they're approved together.

Backend changes explain themselves

When a layout hash or contract version changes, the affected checkpoints arrive labelled layout_changed, so the reviewer knows why they moved before opening the diff.

Housekeeping shows up as statuses

A checkpoint a flow no longer captures reads missing and is approved for removal. A baseline with no run in 30 days is flagged as possibly dead. New checkpoints read new.

Flows stay stable by targeting ids (Compose testTag, resource-id), never on-screen text, as ADR 0001's contract-ID rule requires. Once a CI lane exists, baselines should live where the UI change is reviewed. Committed to the app repo with Git LFS, the new images show up in the pull request that changed them. Until then, approving locally in the dashboard is enough.

Your question

How are screenshots checked across device sizes?

A pixel baseline never carries across screen sizes: layouts reflow and text wraps differently. So there are two layers, each doing what it's good at.

Layer 1 · pixel baselines

A fixed matrix of device classes, not phone models

  • About three classes that bracket the fleet: a small phone, the common 393–412 dp width, and a large or foldable screen if supported.
  • Plus font scale 1.3 and dark mode where the app supports them.
  • Emulators with fixed profiles in CI, for the same system image and fonts and no vendor skin. The Vivo stays for smoke runs.
  • The key is resolution + density + font scale + theme. An unknown class reads new, never a false diff.
Layer 2 · checks at any size

Layout rules from the view hierarchy, no baseline needed

  • Key elements are visible and fully on screen, not clipped.
  • Interactive elements don't overlap.
  • Touch targets are at least 48 dp.
  • Key labels aren't cut off with an ellipsis.
  • Nothing sits under the status bar or the navigation bar.

This layer covers every device and cohort, including the ones with no pixel baseline.

One experiment before layer 2: Maestro 2.10 saves a view hierarchy only for failed or warned steps. Try an intentionally optional assert at each checkpoint, maestro hierarchy between flow segments, and uiautomator dump (checking it doesn't clash with Maestro's driver).

Carried over from swagperf's existing rules

Guards that keep the gate honest

An empty run never passes

Zero screenshots is an error, the same way an empty trace is refused.

Baselines never cross devices or cohorts

Like "never assert our budgets on another app": a different key reads new, never a comparison.

Device prep is always undone

Animations off and SystemUI demo mode (frozen clock, full battery) for this lane only. Both are restored afterwards, and perf captures warn if animations are still off.

One user of the phone at a time

Visual runs take the same capture lock as Perfetto and Flashlight, and refuse to start while another profiler is running.

Why it's parked, and what brings it back

Revisit when any of these happens

  • aWork starts on ADR 0001's Maestro CI lane or its contract registry.
  • bA UI regression reaches a build that a screenshot would have caught.
  • cA phone where Maestro drives Swag Pay without the Vivo hang is attached, or an emulator lane exists.
  • dSwag Pay has cohort test accounts or a forced-cohort override.
  • eYou ask for it.

Watch out for

  • Home's live camera preview must be masked, or Home always fails.
  • Maestro's device server hangs on the Vivo after Store→Rewards.
  • Use JDK 17 or 21. Java 25 hangs Maestro's Android driver.
  • No screenshot ever goes to the model.
